# 三端远程控制的实现与验收

| 能力 | 现有实现入口 | 后续验证 |
| --- | --- | --- |
| Windows 与 macOS 跨屏 | `src/edge.js`、`src/layout.js`、`src/service.js` 负责布局、焦点和控制会话。系统桥接层负责捕获与执行。 | 两台桌面分别作为主机，覆盖负坐标显示器、不同缩放、边缘往返和按住修饰键换屏。 |
| 手机控制桌面 | Android 的 `TouchpadView.java` 与 `LinkService.java` 经已授权的设备组会话发送输入。 | 两个不同桌面分别接收点击、拖动、滚轮和组合键。 |
| 桌面或手机控制 Android | 被控端在 `LinkService.java` 检查功能开关、对端授权及系统执行能力。助手的虚拟鼠标实现位于 `VirtualHid.java`。 | 逐项撤销对端授权、停止助手、撤销投屏，检查另一项能力能否继续使用。 |
| 桌面蓝牙 | `src/input-transport.js` 对接 Windows 的 `native/windows/Hid` 和 macOS 的 `BluetoothHid.swift`。绑定、报告订阅与目标支持的会话协议共同决定可用性。 | 分别记录普通 HID 主机及安装 LanLink 的接收端结果。自定义蓝牙特征的收发成功不能证明系统 HID 主机接受报告。 |
| 远程画面 | 桌面的 `src/video.js` 和 Android 的 `VideoHost.java` 独立管理视频会话。 | 只开启屏幕查看权限，保持输入助手离线。随后单独申请输入并检查手机上的授权提示。 |

## 路由行为

桌面服务的设备状态列出 Android 的输入通道。Android 对端必须明确提供光标会话能力，才能作为设备组内的蓝牙跨屏候选。网络输入按功能开关、系统授权和当前对端授权分别判断。Web 设备卡显示当前或待选通道，新版 Android 提供后端名称时也显示后端。开始控制时仍会向对端重新检查权限并获取控制会话。

辅助网络或 USB 路径通过身份校验后，与主链路比较三次往返耗时。已有辅助路径可用时，新候选需比它快超过 2 ms。持续探测时，活动路径连续三次慢于主链路的 1.5 倍加 5 ms 才因延迟退役。主链路比较超时会中断计数。辅助路径自身断开仍走原有故障处理。该策略仅适用于辅助链路，蓝牙继续遵守用户设置的通道偏好和会话租约。

## 实机验收与待实现模块

1. 每个方向至少记录 1,000 次移动。分别记录源端入队、目标端执行和源端收到确认的时间。报告 P50、P95、超时数、连接方式及显示缩放。跨机单向时延需要时钟偏差估计及误差范围，往返耗时单独报告。
2. 按住 Shift 和鼠标左键分别断开活动通道。从断开时刻记录到判定失效、发起回退、恢复输入的三个时间点。目标是 2 秒内判定并尝试恢复。逐项检查目标端松键、重复点击、视频存续和文件传输结果。
3. Android 无障碍需要单独的手势执行器及用户启用入口。能力协议应区分绝对触摸、相对移动和物理按键。只具备手势时可用于远程画面的触控，跨屏光标和完整键盘需要单独验证。
4. Android 作为蓝牙外设需要实现 HID Device 注册、前台生命周期、绑定目标选择、报告和断线释放。桌面作为外设时，需在目标手机验证配对、系统鼠标识别、报告送达和断连恢复，再由 Android 接收端实现并声明光标会话能力。
5. iOS 首先验证作为外置键鼠接收端的可用操作，分别记录系统版本、配对方式及指针设置。网络输入注入和屏幕采集需要独立的可行性验证。
