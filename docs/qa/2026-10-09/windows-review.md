# LanLink Windows 与跨平台体验审查

日期：2026-10-09（Asia/Shanghai）

## 本轮证据边界

- 当前工作目录版本为 `package.json` 0.3.45，包含大量用户已有未提交修改；本审查未修改产品代码或用户配置。
- 主机为 macOS / arm64。已检查命令环境，未发现 `dotnet` 或 `wine`。没有运行 Windows WPF 窗口、Windows 原生键鼠、注册表、任务计划、Explorer 拖放或 Windows 打包。因此以下“确认”指当前源码的数据流或交互定义已确认，不等于 Windows 实机复现。
- 已审查：Windows 所有 15 个 C# 文件、WPF 样式、Windows 构建/打包脚本，及相关 Mac 设置/配对/暂存实现、服务 action/状态/暂存实现。检索了现有自测与发布说明。
- 正常业务的原生验证仍应在 Windows 10/11 x64 上执行，现有历史验证不能替代当前未提交工作树的重新构建与测试。

## A. 当前源码可确认的问题

### W01 · P1 · 远控失败与重连提示实际不可见

**操作/条件**：打开远控窗口，目标随后离线、输入/屏幕权限被撤销、出现控制冲突、H.264 解码失败，或在“输入文本”窗口中发送失败。

**证据**：`desktop/windows/Remote.cs:21` 创建 `status`，但整个文件没有将其加入任何视觉容器。`:124` 只把 `status.Text` 复制到 `stats.ToolTip`；统计栏在 `:126` 位于默认隐藏的侧栏内；默认折叠见 `:111` 及 `desktop/windows/WindowSize.cs:26`。`:185`、`:211`、`:235–245`、`:260` 与 `:266–269` 的错误都只改这个不可见状态。可见模式标签仍只有“正在控制/仅查看”。

**体验后果**：用户看到黑屏或旧画面，却不知道正在重试、对方拒绝还是操作已经失败。侧栏展开后还需要主动悬停才能读到解释。“输入文本”模态窗也没有自身的错误区。

**建议**：把连接/失败状态放在画面覆盖层或常驻底部区域；错误时显示明确原因与“重试/结束”按钮；模态文字输入错误显示在模态窗内。正常码率等统计可以继续折叠。

**验收**：侧栏保持折叠时，分别制造断网、权限撤销、控制冲突及文字发送失败；当前窗口必须可直接看到正确状态，重试成功后状态恢复，不用悬停、不用切回主窗口。

### W02 · P1 · 多个侧栏页面的通用失败提示被写入隐藏设备页

**操作/条件**：暂存页点“开始传输/查看文件/移除”发生错误；剪贴板历史记录到期后点“复制”；安卓授权概览调用失败；当前页面上服务意外退出。

**证据**：`desktop/windows/Main.cs:58–59` 的 `Notify` 只写 `notice`，另仅对可见设置页写 `settingsStatus`。`notice` 实际属于设备页（`:84`、`:99`）；`HideContent` 会隐藏设备页（`:400`）。暂存操作统一 `main.Run`（`desktop/windows/Staging.cs:24–28`），剪贴板复制同样走 `Run`（`Main.cs:541`），安卓授权概览走 `Run`（`:409–420`）。这些页面没有承接通用通知。服务退出也只调用 `Notify`（`:111`）。

**体验后果**：失败看似“点击无效”。用户必须自行猜测并返回设备页才可能看到错误。注意独立 ADB 引导窗、USB 授权子页、设备权限页已经有局部错误区，不应把所有 ADB 场景一概说成没有反馈。

**建议**：把应用级通知区放到所有页面共享的外层；每个异步动作增加进行中和失败状态。服务退出时当前页直接显示可恢复操作。

**验收**：在上述每一页独立注入错误，原地可见；服务退出提示全局可见；关闭/离开某页不抹掉尚未确认的重要错误。

### W03 · P2 · 保存期间仍可修改的设置会被静默覆盖

**操作/条件**：点“保存设置”后，响应尚未回来时改变停留时间、切换方式、边缘光效或剪贴板开关。

**证据**：`desktop/windows/Main.cs:553` 只禁用保存按钮、设备名、主设备和 `settingsPermissions`；其他设置仍可编辑。`:556` 已把当时值作为参数送出；`:557–558` 收到状态后无条件 `LoadSettingsDraft()`；`:545–550` 覆盖全表并清除 `settingsDirty`。后一次操作因此消失，界面还显示“本机设置已保存”。Mac `desktop/macos/LanLink.swift:923–927` 同样在保存后 `load()`，`:930` 仅禁用保存按钮，需一并回归。

**建议**：保存期间禁用同一批待保存字段，或用草稿版本号保留请求发出后的编辑并继续显示“未保存”。不要把整个服务回包直接当作当前草稿。

**验收**：人为延迟设置响应 2 秒，保存过程中继续编辑；新编辑要么不能进行，要么完成后保留且仍显示未保存，不能被覆盖。

### W04 · P2 · 从 Mac 复制显示中的配对码到 Windows 会被拒绝

**操作/条件**：在 Mac 的配对页复制显示为 `1234 5678` 的八位码，粘贴到 Windows 的加入组输入框。

**证据**：Mac 配对展示允许文本选择（`desktop/macos/LanLink.swift:1015`），输入端自动滤除非数字（`:1022`）。Windows 也以四位分组显示（`desktop/windows/Pairing.cs:107`），但粘贴处理 `:66` 只允许 `^[0-9]{1,8}$`，遇空格直接 `CancelCommand()`，没有错误提示。

**建议**：三端统一接收数字配对码，清除首尾空白及内部普通空格/不换行空格/分组符，再校验八位；提供“复制配对码”按钮，复制纯数字。

**验收**：纯数字、分组空格、尾部换行、跨平台复制均正确；错误长度/混入字母有明确提示，不得静默吞掉。

### W05 · P2 · 权限列表自动刷新会销毁正在操作的控件

**操作/条件**：用 Tab 在“本组设备权限”页移动焦点，停留数秒，或边读权限说明边操作开关。

**证据**：`desktop/windows/Permissions.cs:13` 每 4 秒刷新；`:23–29` 每次都调用 `Display`；`:33` 无论数据是否变化都 `content.Children.Clear()`，随后重新创建所有行和开关。没有内容签名、局部更新或焦点恢复。

**体验后果（需 Windows 实机确认具体焦点落点）**：正在聚焦的元素被移出树，键盘/读屏操作中断，正在瞄准的开关被替换。操作失败提示也可能在下一次正常刷新时被 `:62` 默认文案覆盖。

**建议**：只更新有变化的数据项，保留稳定的控件和焦点；请求中的行不重建；错误提示采用独立生命周期。

**验收**：焦点停在指定开关上超过 12 秒，仍能用 Space 改变同一项；刷新不把滚动位置、读屏焦点或尚未处理的错误清掉。

### W06 · P2 · 设备服务退出后只有重启文案，没有恢复入口

**操作/条件**：子服务进程退出或启动超时。

**证据**：`desktop/windows/Client.cs:48–56` 报“请重新启动”；`desktop/windows/Main.cs:111` 停止轮询并将设备标为离线。`Client.ready` 是实例内只创建一次的完成源（`Client.cs:21`）；现有 UI 没有重新建 Client / 重新启动服务的入口。用户点击主窗关闭按钮又只会隐藏到托盘（`Main.cs:118`），再次双击程序会提示“已在运行”（`:772`），不构成重启。

**建议**：提供“重新连接设备服务/重启 LanLink”的显式按钮和状态；失败后别让用户经历“关窗→重开→已在运行→找托盘退出”的循环。自动恢复应处理旧进程和待完成调用，保留用户草稿。

**验收**：让子进程退出，在当前页一步恢复；重复点击恢复不会生成双实例；主机或端口仍不可用时有清楚错误。

## B. 可直接定位的体验改进，未归类为已实机复现故障

### W07 · P2 · 文件永久保存缺少常规按钮及键盘路径

- 已接收项只有“查看文件”和“拖到文件夹以保存”（`desktop/windows/Staging.cs:24–26`）。拖拽文本是只有鼠标事件的 `TextBlock`，不是可键盘执行的按钮。Mac 同样主要依赖拖拽（`desktop/macos/Staging.swift:75–86`）。打开文件不等于选定一个永久保存目的地。
- 建议加“保存到…”、“在文件夹中显示”，用标准目录/保存对话框；保留拖拽。保存成功并验证目标后再移出暂存区，重名覆盖需明确处理。
- 验收：仅键盘可选定目录、保存文件/文件夹并确认完成；取消、无写权限、重名、磁盘不足时保留暂存原件。

### W08 · P2 · 大文件传输缺少暂停/取消

- `desktop/windows/Staging.cs:27–28` 对 receiving 项不给重新传输/移除操作；底层 `src/staging.js:81` 也明确拒绝传输中移除。不能仅补一个会被后端拒绝的按钮。
- 建议实现任务取消（关闭接收流并清理临时文件），UI 显示“取消传输”；之后允许重试。有多个排队任务时显示队列位置，至少能取消当前项而不退出整个应用。
- 验收：限速发送大文件，随时取消后网络/磁盘活动停止、原文件仍在、其他连接可用；重试正常。

### W09 · P2 · 相同设置在不同平台的生效时机不一致

- Windows 剪贴板与边缘光效变更属于草稿，等“保存设置”（`Main.cs:584–594`、`:556`）。Mac 对同名开关立即发送 settings（`LanLink.swift:950–951`、`:958–960`）。Windows 的外观与启动又是立即应用（`Main.cs:576`、`:580`），形成同页混合语义。
- 建议统一立即保存，或把“立即生效”和“需要保存”明确分区并逐项标识。对自动上传剪贴板的关闭操作优先保证用户能立即理解当前是否仍在上传。
- 验收：关闭自动上传后，用户无需猜测生效状态；三端文案、保存提示和实际传输行为一致。

### W10 · P3 · Windows 发布版本元数据未统一

- 当前桌面/Android 为 0.3.45，但 `desktop/windows/app.manifest:3` 的 assemblyIdentity 仍为 0.3.3.0；Windows 构建源未见与 package.json 同步的 AssemblyFileVersion / AssemblyInformationalVersion。
- 这不能仅据 manifest 推断 Explorer 最终显示版本，需检查本次构建产物。建议构建时统一生成 manifest / assembly 版本，并让“我的信息”显示应用版本、架构及可复制诊断信息。
- 验收：EXE 文件属性、应用信息页、包名、服务版本、Android versionName 可对应到同一发布版本；报告问题无需用户猜版本。

## D. 核心发现交叉复核追加

复核了 `/tmp/lanlink-core-extra.mjs` 与 `/tmp/lanlink-core-extra.log`，另外独立编写并运行 `/tmp/lanlink-clipboard-crosscheck.mjs`，进程退出码 0。使用当前真实 Service / ClipboardSync / nativeEvent / 文件读取与接收逻辑；仅系统剪贴板和 peer 传递是内存替身，未操作用户系统剪贴板，也不等于真实两台设备联调。两项复核均确认。证据输出：

### C01 · P1 · 回切到自己先前复制的文字被误当成回声

- 正常条件：默认自动上传/下载开启。A 在普通应用复制 X，B 收到；B 复制 Y，A 收到；A 重新复制 X。两次内容之间确实发生 X→Y→X 的系统剪贴板变化，应该发出新的同步事件。
- `src/clipboard-sync.js:14` 同时抑制 `applied` 与历史 `lastLocal`。A 首次上传后 `lastLocal=X`（`:29`）；收到 Y 时只更新 `applied=Y`（`:15`，`src/service.js:307`），未清除 `lastLocal`。A 重新复制 X 仍被 `:28` 拦截，组最新内容继续是 Y。
- 独立探针从实际 `nativeEvent({type:'clipboardChanged'})` 入口执行；最终 A 系统内容 X、B 系统内容 Y、A 的组 latest 仍 Y。额外模拟一次系统剪贴板通知也不能恢复。属于常见来回复制流程的问题，不是合理的相同内容防回声设计。
- 建议区分“本次应用回写事件”与“上一次本地发布值”；收到/应用远端内容后旧的本地指纹不应永久屏蔽再次复制。验收覆盖 X→Y→X、X→Y→Z、同值重复通知无风暴，以及多设备返回旧内容。

### C02 · P2 · 同一文件重复手动上传，淘汰的恰好是仍在发布的分享记录

- 复现条件需明确：十分钟内发送方总计 21 次手动上传未改变的同一文件；接收方关闭自动下载，之后手动获取该最新文件。也可以是接收方较晚上线才下载。它不是“发送文件到暂存区”按钮的问题，不能混写成日常每次发文件都失败。
- `src/service.js:275–282` 每次 snapshot 先创建新 offer，并仅保留 20 条普通 offer；`src/clipboard-sync.js:25–26` 的手动去重分支随后又发布旧 latest。重复满 21 次后旧 latest 仍被广播，但其文件条目已经被淘汰。
- 原核心探针无真实接收者，结论来自 `fileBytes` 失败；独立探针补了接收方 `apply(latest)`，确实走文件接收链失败：“文件分享已过期或范围无效，请重新复制”。因此不是只看 Map 内部值的假阳性，但属于较低频边界场景，优先级低于文字回切。
- 建议去重在新建 offer 前完成，或复用并保活仍在发布的文件 offer；缓存淘汰避免删除当前 latest，过期时创建新的有效 latest。验收 1/20/21/50 次重试后最新文件都能下载，不增加无用记录。

### C03 · P1 · Mac 无法仅撤销某台 Android 成员对本机的持续权限

- 当前组成员默认可信（`src/consent.js:13`）。Mac 设备菜单的“撤销此设备的本机权限”被 `device.platform != "android"` 隐藏（`desktop/macos/LanLink.swift:516`）。权限页的非本机设备只有状态，没有控制该设备访问本机的开关；`:799–803` 仅给本机卡全局功能开关，写入 `settings.permissions`（`:127–134`）。Windows 也有相同排除条件（`desktop/windows/Main.cs:325`）。
- “ADB 键鼠授权”解决电脑控制手机的方向，不是手机访问这台电脑的权限，不能替代这一缺失入口。
- “取消桌面控制”可停止当前会话，但不是永久撤销：`src/service.js:524–527` 只设置 `pausedPeers`；对方显式发起新会话时 `:226` 自动清除暂停标记。此功能本身符合“结束本次控制”的语义，不应误报为退出保护失效；问题是用户没有可用的单设备持久撤销路径。
- 剩余替代方式是关闭本机全局功能（影响其他电脑）或将手机移出整个组（影响文件/剪贴板等其他合作）。用户无法在保留组和其他设备能力的前提下禁止某手机再次控制 Mac。
- 建议恢复所有成员的“管理此设备对本机的权限”，明确入站/出站方向；至少提供按成员永久撤销，进一步可逐项限制输入/屏幕/剪贴板/关机。后端 `revokeConsent(id)` 已支持按任意设备身份保存全 false（`service.js:161–170`），界面不应按 Android 平台隐藏。
- 验收：组内 Mac + 手机 + 另一电脑，撤销手机对 Mac 的控制后手机重连/显式重新控制必须被拒绝或要求 Mac 确认，另一电脑不受影响；用户可保留允许的手机文件/剪贴板能力。此项为源码交叉确认，未作真实手机到 Mac 入站控制实验。
